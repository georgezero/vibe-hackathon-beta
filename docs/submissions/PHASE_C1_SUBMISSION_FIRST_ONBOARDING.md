### Existing participant flow

- `/submit` is the public entry screen and points to `/register-team`.
- `/register-team` collects team name, owner name, contact email, and owner
  badge number, then calls `POST /api/register-team`.
- `POST /api/register-team` creates a `teams` row, a draft `submissions` row,
  team-member metadata, and (when a GitHub owner is present) a legacy
  `submission_owners` row.
- The lower-level `POST /api/v1/submissions` endpoint creates a draft from
  team name/contact email and returns the private edit token.
- Submission IDs are `sub_` plus an 8-character nanoid. Edit tokens are
  `edit_` plus a 16-character nanoid and are currently retained in the
  `submissions.edit_token` compatibility column because existing tokenized
  routes and agent clients depend on them.
- Existing tokenized routes are `/submit/:editToken`,
  `/submit/:editToken/start`, `/submit/:editToken/preview`, `/submit/:editToken/team`,
  and `/submit/:editToken/done`. Existing API mutation/finalize routes accept
  `Authorization: Bearer <editToken>` and compare it server-side.
- Manual completion, hosted API updates, preview, and finalization are already
  implemented. Agent prompts are generated by the hosted completion prompt
  components and include the submission-scoped API URLs.
- Better Auth users are optional for the current badge-mode participant flow.
  Existing `submission_owners` supports explicit GitHub-owner recovery; no
  email matching is used for ownership.
- The Account page is the authenticated identity/settings hub. Public signed-in
  navigation is role-aware but has no participant My Projects destination yet.
- People & Access uses `PeopleAccessClient`; its create-account surface is
  currently a side sheet and will be centered without changing its provisioning
  semantics.
- Existing audit actions include `submission_created`, `team_registered`,
  `submission_updated`, and `submission_finalized`. Raw edit tokens are not
  intentionally added to audit metadata by the new Phase C.1 code.

### Phase C.1 direction

`/start` becomes the public canonical draft-creation entry while `/submit`
redirects compatibly. The existing tokenized editing and agent API contract is
preserved. A separate additive claim-transaction table and explicit ownership
records provide optional Better Auth claiming; claiming never grants admin or
judge authorization. A participant-facing My Projects view is derived only
from explicit ownership records. Outbound email is not available, so signed-out
recovery continues to require the Submission ID and private Edit token.

## Implementation

- `/start` is the canonical guest-first creation route. `/submit` is a
  compatibility redirect to `/start`; existing tokenized edit, preview, team,
  done, API, and finalize URLs remain unchanged.
- Guest creation uses the existing `POST /api/register-team` contract with an
  explicit `source: "start"` marker. It creates a draft and team metadata but
  does not create a Better Auth user, admin authorization, judge
  authorization, or account ownership row.
- The creation result presents the Submission ID and private Edit token once,
  with copy affordances and a clear warning that outbound email recovery is
  not available.
- `/start/resume` and `POST /api/submissions/resume` verify the exact pair with
  a generic failure response. Resume grants only the existing bounded edit
  authority and never creates a Better Auth session.
- `submission_claim_transactions` is additive, single-use, expiring, and
  browser-bound. It stores only a SHA-256 digest of the Edit token and the
  browser binding. Confirmation requires a Better Auth user and explicit
  confirmation. Claiming never grants administrator or judge access.
- `submission_owners` now has one-owner-per-submission uniqueness and a user
  lookup index. My Projects reads only explicit ownership rows; matching team
  email is never used.
- Logout now clears the two application-owned claim cookies along with the
  existing application session and transaction cookies.
- Agent prompts retain the hosted API and replace-style roster contract while
  explicitly treating the Edit token as confidential bearer access.
- The People & Access create-account dialog is centered at desktop widths with
  constrained height and responsive behavior; provisioning semantics are
  unchanged.

because the established edit URLs and hosted agent API still require the
credential. New claim transactions never persist the raw token. A future
credential-rotation phase should migrate all tokenized routes to a hashed
verification column before removing plaintext compatibility storage.

Submission ID and private Edit token.
